# 全局 Runner 调度

本版本的共享模式使用一台控制器派发独立阶段工作流，替代每堂课固定预留三台的方式。定时规则、订阅课程、自动词库默认开关和邮件触发边界保持原设置。固定两路及 `auto` 入口仍保留。

## 容量与估计

- 同时最多 15 台：1 台控制器，加 14 个准备、ASR、汇总或发布子任务；排队及派发结果未知的任务也占额度。
- 最多 5 个活跃课次，单堂最多 6 个 ASR Worker。块队列按课次隔离，分配的是跨课次可借用的机器名额。
- 预计计算量为待完成原块累计秒数乘以推理/音频耗时比。初始比率取同课程更早已完成课次的中位数，要求同 Qwen 模型和 revision；无可靠历史暂取 2。本堂至少 5 块有耗时后使用实测中位数，范围限制在 0.25–10。
- 以 4500 秒（75 分钟）为初始 ASR 目标，向上取整决定 Worker 数，受剩余块数、六台上限和全局剩余额度限制。安装、排队、准备、复核及摘要另算；实际块成本不同，目标不是 SLA。
- 已准备课次先获得基础服务，再按剩余预计工作量分配额外 Worker；完成课次的汇总、发布优先。空余容量后续可以补进其他长课。已经启动的 Worker 不为缩容而取消。

最多六个静态分组保留原装配接口和覆盖检查，动态领取不受组别限制。未使用的分组没有对应空跑任务，不形成等待屏障。全部原块完成且本堂 ASR 子任务自然结束后才汇总，不等待其他课堂。

控制器本身在等待期间仍占用 Runner；这会增加 Runner 分钟数。六台并行也增加模型安装/初始化及 artifact 下载开销。单堂长课预计更早完成，但多课同时满载和总计算成本必须通过实际运行评估，不能直接将六台视为三台的两倍提速。

## 派发和恢复

`parallel_pilot.yml` 冻结课次与原队列，控制器把阶段预留写入 AES-GCM 加密的 Git CAS 日志后才调用 `workflow_dispatch`。只有确认对应 run ID、nonce、源代码 SHA 和父代际后，子任务才进入课程处理或加载模型。API 请求结果未知时保留名额，不重放派发。

| 分支或产物 | 用途 |
| --- | --- |
| `codex/runner-pool-<parent_run>` | 加密课次状态、派发票据和子 run ID |
| `codex/runner-pool-owner` | 全局批次归属；防止父流程结束后遗留子任务与新批次叠加 |
| `codex/runner-source-<parent_run>` | 冻结阶段工作流代码；main 更新不改变在途任务 |
| `codex/asr-queue-<parent_run>-<slot>` | 原共享块领取及完成结果 |
| 父 run 的 `qwen-production-queue` | 原课次、数据库与历史输入 |
| 子 run 的 `qwen-production-*` | 准备、ASR 本地结果、复核检查点和发布结果 |

owner、派发日志及块队列都只存密文；代码分支只保存已有代码。没有 force push，读取失败不等于空队列。所有临时分支暂保留，人工清理必须确认无活动任务、恢复窗口结束且必要产物已另存。不能删除 owner 或日志来绕过未结束/结果未知的派发。

控制器失败不会取消子任务，也不能视为已释放其名额。新批次，包括旧固定分片入口，在规划前先确认前一批所有派发均已结束；前一批有未知派发或缺失日志则明确停止。控制器自身还用仓库级 job concurrency 串行运行。正常情况下，计划、控制器和批次收尾阶段互不重叠。

恢复方式为**重试父工作流的失败 job**。全部旧子任务先结束，再推进父代际：成功准备复用音频和冻结计划，ASR 先恢复所有旧 Worker 本地密文再领取未完成块，已成功汇总只补发布。子工作流原生 rerun 被拒绝，不能复用同一票据重复执行。慢块没有按时间抢占的租约。

失败课次不会进入摘要；全部子任务结束后，父流程收尾将已保存的失败数据库进度按单堂范围发布或进行隔离合并，保留已有转录及错误计数。此环节只生成独立加密失败归档，不生成 `state.enc`、不制造新的复核额度检查点。

汇总仍校验旧额度检查点的代际。先前汇总已经进入复核但没有对应保存状态时，或者状态更旧、过期、输入不符，都停止额外复核，不重置整堂课 900 秒/40 段额度。完成块不会因为调度数量变化被重新识别。未知派发需人工核查，不能以新批次掩盖。

## 准备与性能记录

分块从已保留的单声道 16 kHz、PCM24 FLAC 按样本位置读取，避免对每个块从头解码全堂音频。逐块样本数、原始边界、重叠和 FLAC 哈希仍检查；只有编码字节可能与原 FFmpeg 输出不同，当前计划保存当前文件的真实哈希。旧准备检查点照常读，不重切旧音频。

准备仍保存完整恢复包，额外生成仅含原块与原 specification 的加密 Worker 输入；ASR 不再下载整堂 FLAC、数据库和 PPT 副本。控制器只读取小型加密计划，不下载音频。汇总仍读取完整原音频供定位和复核。

`prepare-timing.json` 分开记录获取/VAD、分块及检查点保存耗时；子任务 `stage-audit.json` 区分输入下载和处理时间；`worker-audit.json` 继续记录真实 Worker 工作。总成本还须使用各子 run 的实际 jobs/steps，包括排队、依赖安装和控制器分钟数。装配分组的累计 decode_seconds 不能代替 Worker 墙钟耗时。

## 验证和启用边界

隔离测试覆盖八课次混合阶段的 15 台总预算、五课次/六 Worker 限制、容量补给和独立汇总，确认失败只阻止对应课次。另覆盖未知派发不重放、CAS 竞争、旧子任务阻止新批次、票据/代际验证、旧汇总额度保护及原流程兼容。真实本地 Git 验证日志加密和冲突；合成音频与旧 FFmpeg 逐样本比较，包括重叠和非整秒边界。

这些测试不登录 iCourse、不调用模型、SMTP 或正式数据库，不证明新控制器的云端派发、速度及课堂准确率。旧共享队列的真实课堂证据不能替代新编排的验证。新子工作流须先在默认分支注册才能按 GitHub 的文档保证可派发；正式启用后的首堂应观察全部子 run 和总成本，保留隔离发布/不发送邮件的试跑选项。

GitHub 原生支持使用 `GITHUB_TOKEN` 触发 `workflow_dispatch`，不需要新增 PAT；控制器因此使用 `actions: write`，子任务只用 `actions: read`。参考 [token 触发规则](https://docs.github.com/en/actions/concepts/security/github_token) 和 [手动工作流条件](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)。
